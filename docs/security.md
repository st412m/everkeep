# Security

What protects the server and the vault: the token, where the server listens, the vault boundary, the write policies, and what each part of the server is allowed to do. Read this before exposing Everkeep beyond your own computer, or before pointing it at a folder with sensitive files.

## The token

Everything over HTTP needs the token. It comes in one of two ways:

- in the path: `/private_<token>/mcp` — for claude.ai custom connectors, which cannot send headers;
- in a header on `/mcp`: `Authorization: Bearer <token>` — for every other client.

The token is generated by the server (32 random bytes, 64 hex characters), saved in the state directory with mode 0600, and printed only at the moment it is generated and by `everkeep token`. A token you bring yourself must have at least 32 characters. The token is compared in constant time. Neither the token nor a request path is written to any log; the request log masks it as `/private_***`.

Answers to a wrong request say as little as possible:

- a wrong or missing token in the path, or any other path: 404 with an empty body;
- `/.well-known/…`: 404, so clients see a server without OAuth and do not try to start a login;
- a `Bearer` header with a wrong token: 401 with an empty body.

There is no OAuth and no user accounts: whoever has the token has the server. To replace it, run `everkeep token --new`, restart the server and update every client.

## Where it listens

By default `everkeep serve` listens on `127.0.0.1`, so only programs on the same computer reach it. On such a local address it also refuses, with 403, any request whose `Host` or `Origin` header is not local. A website in your browser cannot use a DNS trick to send requests to it. The names in `allowed_hosts` are accepted as well: the public name of your own tunnel or proxy on the same computer, which forwards requests only after TLS.

On any other address (`--host 0.0.0.0`, and inside the Docker image) these checks are off and the token alone protects the server; the start line says so. Publish the port only to `127.0.0.1` on the host (`-p 127.0.0.1:3100:3100`), and reach it from outside only through TLS: a tunnel or a reverse proxy, see [remote access](remote-access.md). Everkeep itself speaks plain HTTP.

## The vault boundary

Every path a tool receives is checked before anything is read or written:

- a path outside the vault, one that climbs out with `..`, and a sibling directory whose name starts with the vault's own (`/srv/notes_old` next to `/srv/notes`) are refused with `PATH_OUTSIDE_VAULT`;
- a path through a symlink is checked at the place it resolves to, including a symlink that leaves the vault and points back in, at the destination of every write;
- the check lives in one module, and the modules behind it accept only a path that went through it.

The state directory, with the token and the document cache, must be outside the vault; the server refuses to start otherwise. No tool can read it.

## Write policies

The assistant cannot change the rules it works under. MCP tools refuse to create, change, move or discard any file or directory named `.vault-policy`, in any letter case and in any position of a path. Markers are written only by `everkeep policy` on the server and, in the Home Assistant app, by the Vault policies page; the code that serves the tools has no reference to the code that writes markers. A broken marker locks its zone instead of opening it. See [write policies](policies.md).

## What a leaked token gives

Within the vault and its policies, everything the assistant can do: read every file, write and edit where the policies allow, discard into trash directories. It does not give: anything outside the vault, the token file or the cache, changing a policy, deleting a file outright, or writing to a SQLite database. Replace the token at once (`everkeep token --new`, restart) and look at recent changes; the trash keeps what was discarded until its auto-purge.

## The Vault policies page (Home Assistant)

In the Home Assistant app the page runs in the same process on its own port, reachable only through Home Assistant ingress. It accepts connections from the Supervisor address `172.30.32.2` only, never through the token URL. Home Assistant shows its sidebar entry to administrators only but serves the page to any logged-in user who opens its address; the app option `policy_page_users` limits it to the listed users, and a forged second user header is refused.

## What each part may do

- `grep_files` runs in a child process that is killed after 10 seconds, so a runaway regular expression cannot hang the server.
- Documents are extracted in worker threads with a timeout and a 1 GB memory cap, one at a time.
- SQLite runs as `sqlite3 -readonly -safe`: no writes, and `ATTACH` and the other ways out of the vault through SQL are disabled; every call has a 256 MiB memory limit.
- External programs (`pdfinfo`, `pdftoppm`, `sqlite3`) are started with an argument list, never through a shell.
- There is no recursive delete anywhere; auto-purge removes old files from a trash one at a time.
- The Docker image runs as an unprivileged user (user id 1000).
